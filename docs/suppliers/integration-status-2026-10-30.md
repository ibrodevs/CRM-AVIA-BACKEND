## TTBooking: изменения

- SEARCHFLIGHTS/SEARCHRESULT и SELECTFLIGHT/SELECTRESULT вызываются по одному разу, без циклического опроса RESULT. Пустой токен поиска — пустая выдача.
- CREATERESULT перенесён в создание брони: он может создавать заказ у поставщика. Автоматический status inquiry вызывает только DISPLAYSTATUS/DISPLAYTICKETS.
- Добавлено явное возобновление: CREATEBOOKING повторяется только с тем же selection token и тем же HMAC-отпечатком исходных пассажиров/контакта; CREATERESULT использует тот же prebooking ID. Изменённые данные запрещают повтор; потерянный результат оплаты этим действием не повторяется.
- Встроены подтверждённые статусы bookingFile и CREATERESULT. Пользовательский status_map не управляет финансовыми статусами. Неизвестные, OPERATOR, REQUEST_STATUS и EXCHANGE не считаются успешной выпиской.
- Оплата/выписка — только PAYDEPOSIT при свежем NEW и неистёкшем подтверждённом тайм-лимите. SELECTFOP/ISSUETICKETS не вызываются.
- До платежа сохраняется marker. При неоднозначном ответе повторное списание заблокировано; проверка COMPLETE получает реальные билеты через DISPLAYTICKETS.
- При явном синхронном отказе `NOT ENOUGHT MONEY` вместе с bookingFile.status=NEW операция остаётся невыполненной: workflow item остаётся booked, выставляется INSUFFICIENT_DEPOSIT. После пополнения возможен новый ручной запрос; автоматического повтора нет.
- Билеты читаются из `bookingFile.reservations.reservation[].products.airTicket[]`. Используются number/carrier/passenger/recordLocator самого билета. PNR уровня reservation может быть пустым; несколько PNR сохраняются отдельно.
- Билет сопоставляется с участником CRM по HMAC нормализованных паспортных полей, без сохранения паспортного echo в логах или билетном snapshot. Контакты пассажира берутся из CRM; при отсутствии используются контакты оформления.
- Исправлены реальные особенности выдачи: token=0 сохраняется; числовая ISO-валюта 643 становится RUB; строковое count нормализуется в число; исходный поисковый token сохраняется для следующей перепроверки.
- Добавлен отдельный подтверждаемый пользователем войд. VOID обновляет уже существующие Ticket, без создания фиктивного возврата. Возврат и обмен через API не предлагаются.

## i’way: изменения

- Общий sandbox-доступ из п.6 руководства используется в live acceptance, без запроса несуществующих персональных sandbox-реквизитов. Реквизиты не добавлены в исходники/каталог провайдеров.
- Поиск и перепроверка используют координаты, currency, current_price_id. Проверяются check-time, allow_booking, возможные дубли и местное время подачи.
- Для каждого пассажира передаются phone/email из CRM или контакта оформления. Это исправило живой отказ «Необходимо заполнить phone».
- Кресла обязательны для детей младше 12 лет; используются infant_seat/seat/booster из выбранного предложения. Несколько кресел одного типа требуют согласования: документированный массив допускает не более одной услуги каждого типа.
- В интерфейсе есть выбор кресел, опциональной таблички и платной дороги. Цены и ID берутся только из ответа поставщика. Уже включённые услуги не оплачиваются повторно; текст таблички при необходимости заполняется именем первого пассажира.
- Уточнён состав цены: стоимость в ответе заказа уже включает выбранные допуслуги. Повторно прибавлять их нельзя. Перед approve текущая стоимость сверяется с согласованной.
- Создание и approve разделены. Успешный approve с payable_status=1 и status=0 означает подтверждение оплаты с ожиданием обработки, а не назначенную/исполненную поездку; UI показывает это явно, status inquiry продолжает чтение.
- Если ответ создания потерян и transaction неизвестен, разрешено явное создание замены только до любого approve, с перепроверкой предложения и журналом брошенных попыток. internal_number не используется для поиска/идемпотентности поставщика. Неопределённый результат approve запрещает создание замены.
- Отмена рассчитывается через свежие trips/check-cancel: 0% либо 100% текущей подтверждённой стоимости. Для отмены со штрафом UI показывает сумму, backend проверяет короткоживущую подпись согласия и повторно сверяет условия. При отсутствии точной стоимости отмена со штрафом блокируется.
- Неподтверждённый черновик не передаётся в обработку. Для него предусмотрен явно обозначенный отзыв в CRM с запретом последующего approve, без выдуманного подтверждения отмены со стороны поставщика.
- Уведомления пассажиру/заказчику через send_params отключены во всех тестовых запросах.

## Новые действия CRM и права

- `POST /api/v1/booking-workflows/{id}/resume/`: отдельное возобновление неизвестного создания; services.book + доступ к заказу/виду услуги.
- `POST /api/v1/booking-workflows/{id}/void/`: явное подтверждение войда TTBooking; services.cancel + доступ к заказу/виду услуги.
- `POST /api/v1/booking-workflows/{id}/cancel-transfer/`: получение расчёта и отдельная отправка подписанного согласия; services.cancel + доступ к заказу/виду услуги.
- Status inquiry остаётся чтением. Создание, оплата и отмена сериализованы supplier lease; подписанный расчёт отмены не позволяет подставить клиентскую цену.
